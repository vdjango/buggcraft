# P2P 与中转验证记录

验证日期：2026-10-21。

默认连接策略为自动：每个加入者单独尝试 P2P，协商失败或超时后走房间节点中转。加入者也可以指定仅中转。同一房间中的路径互不绑定，房主不必为全房间选一种方式。标准启动器接入使用 JSON-RPC bridge，接入方无需实现 ICE、打洞或切换逻辑。

## 验证结果

- 本机真实端到端测试：房主和访客完成 2 MiB 双向传输以及并发流；测试禁止游戏流打开中转通道。退出后检查 WebRTC 连接关闭、访客本地监听端口释放。
- 混合房间测试：一个直接访客、一个仅中转访客、一个模拟 UDP 不可用并自动降级的访客同时加入；各自逐字节校验双向负载，确认只有中转访客计入节点游戏流量。
- 故障测试：无 ICE 应答时限时切换中转；另一位 P2P 访客仍保持直连并继续传输。也验证既有 P2P 流失败后不重放旧 TCP 数据，新建游戏连接可复用同一游戏地址并通过中转。
- 公网跨系统测试：Windows 房主与 Ubuntu Linux 访客通过公网节点协商，完成 P2P 双向 256 KiB 数据验证；结果记录在 `minecraft-tunnel/config/remote-test/public-peer-result.json`。
- 三个隔离公网预览节点的 UDP STUN 均通过外部探测。节点网页、启动器接入说明及标准 bridge 混合房间示例已检查桌面和移动布局。
- 相关回归：peer transport、bridge、room lifecycle 共 16 项通过；启动器布局、加入流程及节点可用性共 82 项通过。服务端完整回归此前 38 项通过、启动器服务端集成 62 项通过；后续补充的超时降级测试单独执行。

## 边界

P2P 会让两个玩家的网络地址互相可见；仅中转模式避免房间成员直接交换候选地址。自动策略优先直连，因此不适用于需要隐藏访客公网地址的场景。部分网络可能无法建立直连，届时使用节点中转。当前公网实测覆盖 Windows 与 Linux，不代表已覆盖所有 NAT、防火墙、运营商 UDP 策略或 IPv6 环境。

切换路径只作用于新建的游戏 TCP 连接。已有 TCP 会话中断时，需要 Minecraft 客户端重新连接；不会把部分已发送的数据自动重放到另一条连接。P2P 节省节点带宽，但无法抵御对等玩家网络的 DDoS，也不能保证节点本身不受攻击。
