# 整合包缺失模组处理

未公开发布的本地模组，在当前导出流程中直接随包保存。导入时从包中恢复，不要求发布到模组平台。

旧包或外部整合包引用的模组已不可用时，导入会列出缺失模组，等待用户选择「跳过并继续」或「停止导入」。没有明确同意不能跳过；关闭弹窗、按 Esc、取消任务和退出启动器都可以停止等待。下载和安装仍在后台运行，等待选择不会阻塞 UI。

弹窗说明：模组可能未发布或已下架；跳过必需模组可能导致游戏无法启动。联机时，若房主正在使用这些模组，需要向房主索要并放入实例的 `mods` 文件夹；房主没有使用的模组无需补齐。

## 识别范围

- Buggcraft / Modrinth 包的 `mods/*.jar` 下载在来源尝试结束后报告 HTTP 404 / 410。
- CurseForge 已知模组项目的指定文件记录缺失，或版本尚未公开。项目不匹配仍作为错误处理。
- 超时、授权失败、网络断开、磁盘错误、哈希校验失败继续使用原来的失败重试流程，不能据此判定「未发布」。
- 游戏核心、加载器、libraries、assets、资源包、光影和包内损坏文件不进入模组跳过流程。

确认跳过之后，其余文件仍按原规则下载和校验。实例以原有事务方式保存；跳过清单写入 `buggcraftModpack.skippedMods`、`buggcraft-modpack.json` 和任务历史，完成提示会显示跳过数量。跳过项不伪装成已安装资源。停止之后重试会复用已下载文件，并重新检查缺失情况，不沿用旧的同意结果。无交互调用者没有提供确认回调时，默认保留严格失败行为。

## 自动化验收

| 测试入口 | 验证内容 |
|---|---|
| `tests/test_modpack_missing_mods.py` | 本地 HTTP 真下载、404 与校验失败区分、Buggcraft / Modrinth 选择继续、停止后复用缓存重试、未发布模组随包导入、CurseForge 缺失元数据、取消等待 |
| `tests/test_modpack_missing_ui.py` | 真实 QML 点击跳过与停止、Esc 停止、等待期间 UI 计时器正常、文件落盘与完成提示、停止后恢复下载、随包本地模组无弹窗 |

这两组测试接入 `package.yml` 和 `client-regression.yml`，可以通过标准测试入口运行：

```powershell
python -m pytest -q tests/test_modpack_missing_mods.py tests/test_modpack_missing_ui.py
```

用例使用可控本地 HTTP 文件验证生产导入器和 UI，不将其记作真实 Minecraft 或多人游戏运行测试。跳过缺失模组也不承诺游戏可启动。
