# 好友与多客户端联机回归

这份文档包含两部分：可执行的自动化，以及供发布验收使用的操作测试用例。测试结果与截图留在每次运行的独立目录，不能用上次通过的产物代替本次运行。

## 一、自动化

### 状态与真实点击回归

在启动器仓库执行：

```powershell
.build-venv/Scripts/python.exe -m pytest -q tests/test_friend_entry_regression.py tests/test_friend_entry_ui.py tests/test_chat_controller.py tests/test_friend_directory.py tests/test_lobby_opening.py tests/test_lobby_navigation.py tests/test_lobby_layout.py tests/test_social_diagnostics.py
```

`test_friend_entry_regression.py` 覆盖首次连接失败、连续 100 次刷新失败、成功恢复、配置临时无法读取、强制刷新时配置无法读取、真实更换身份、旧请求迟到、切回匿名、删除节点、个人码过期、响应格式损坏。失败时保留的联系人一律标记在线状态未知。

`test_friend_entry_ui.py` 创建完整启动器窗口，通过 `QApplication.sendEvent(QMouseEvent)` 定向点击正式 QML 页面，不移动桌面鼠标；覆盖首页入口、大厅悬浮入口、好友窗口关闭后重新打开、筛选、复制好友码、重试与过期换码。它使用受控网络结果，适合快速回归；真实网络由下一项验证。

新增好友回归已接入 `.github/workflows/package.yml` 的打包前检查，失败会阻止打包继续。四游戏验收依赖本地 Java、Minecraft 资产、真实节点和 Windows 桌面，需单独执行并保留结果。

### 客户端点击与真实环境的边界

正式 UI 自动化入口为 pytest：

```powershell
$env:QT_QPA_PLATFORM = 'windows'
$env:BUGGCRAFT_UI_PAUSE_MS = '350'
.build-venv/Scripts/python.exe -m pytest -s -q tests/test_client_ui_acceptance.py::ClientUiMultiplayerTests tests/test_friend_entry_ui.py
```

用例通过鼠标键盘操作真实大厅、节点下拉及好友各页签，保存截图、操作日志和结果。远端响应使用本地夹具，只能证明页面及控制器行为。旧四客户端脚本依赖 Python `tunnel` 服务，已经删除，不能继续作为当前 C++ Bridge 的通过证据。

下表中“四大厅/四游戏”项保留为真实环境验收步骤，目前没有迁移后的 pytest 自动化实现。房主、三名访客和游戏都使用隔离目录，分别验证混合路径与仅中转；实际路径以 C++ Bridge 事件为准，不能把回退中转算作 P2P 通过。

### 原生传输回归

在原生节点仓库构建后执行：

```powershell
python -m unittest tests.test_bridge tests.test_peer_reconnect tests.test_bridge_library -v
```

覆盖真实 SSH/TCP、混合 P2P/中转、三名玩家持续负载、单玩家 SSH 黑洞超时、强制退出回收、压缩尾帧/半关闭、分片、主机身份校验、EXE 与 DLL 互通、640 轮 P2P 流创建后重连、聊天、原生好友签名、模组传输授权与取消/校验失败。测试夹具发送 Minecraft 握手后才进入合成数据流，DLL 错误检查使用 C ABI。

## 二、操作测试用例

前置条件：四份独立测试配置 A/B/C/D，A 与其余三人互为好友；同版本游戏；使用测试节点和独立世界；记录版本、系统、时间与场景。每个失败必须保留诊断包和对应服务器日志，不能删除节点重建来“通过”。

| ID | 操作步骤 | 必须看到的结果 | 自动化对应 |
| --- | --- | --- | --- |
| F01 | 使用个人码启动，首次好友登录前让节点不可达；点击首页好友 | 入口可见；打开好友窗口；显示连接错误；重试按钮执行重试 | 状态回归、点击回归 |
| F02 | 正常显示联系人后连续刷新失败；关闭好友窗口，再从首页、大厅分别打开 | 两个入口均存在；联系人保留；在线状态未知；错误可见 | 状态回归、点击回归 |
| F03 | 在读取已选节点配置时模拟权限/JSON 读取失败；刷新大厅，再恢复文件 | 不改变账号代次、不清联系人；配置错误可见；文件恢复后无需重新登录 | 状态回归 |
| F04 | 真正替换个人码；让旧请求随后才返回 | 清除旧账号数据；旧响应不能污染新账号；新账号好友独立 | 状态回归 |
| F05 | 使用到期个人码，点击好友再点击更换接入码 | 入口保留，明确显示过期，跳到换码页面；禁止新建连接 | 状态回归、点击回归 |
| F06 | 选择匿名码，再删除节点 | 不保留其他账号的好友；个人好友入口按真实能力隐藏 | 状态回归 |
| F07 | 节点返回损坏/缺字段的好友响应 | 结束加载，显示错误，联系人在线状态未知；下一次有效响应能恢复 | 状态回归 |
| F08 | 节点拒绝新的好友账号认证，同时已有游戏连接正常；随后恢复认证 | 明确显示认证失败；好友入口与联系人保留；房间正常；刷新可恢复 | 四大厅/四游戏 |
| F09 | 复制好友码、切换好友/申请/邀请标签、切换在线/全部筛选，关闭再打开 | ID 正确，标签和未读计数符合操作，故障时不把未知联系人计为在线 | 点击回归、已有通知回归 |
| G01 | A 点击创建、复制邀请码；B/C 自动选路加入，D 手动选择中转加入；四个游戏进服 | B/C 实际 P2P，D 实际中转；服务器同时有四名玩家 | 四大厅/四游戏 mixed |
| G02 | B/C/D 均点击选择中转并加入；四个游戏进服 | 三名玩家均实际中转，四人可同时游玩 | 四大厅/四游戏 relay |
| G03 | 四个游戏分别键盘操作、鼠标挖方块和放方块 | 服务器确认每个玩家都完成 stone → air → dirt 世界变化 | 四游戏键鼠 |
| G04 | 任一受邀者在大厅发送中文、表情消息 | 四个大厅均收到同一消息，不丢字、不串身份 | 四大厅/四游戏 |
| G05 | B 点击返回、确认断开；检查 A/C/D | 仅 B 离开；房主和另两人会话不变，持续可用 | 四大厅/四游戏、原生回归 |
| G06 | 单独阻断 B 到节点的 SSH，等待超时；A/C/D 继续通信 | B 明确报错；不关闭其他人的桥和房间 | 原生黑洞回归 |
| G07 | P2P 下反复建立/关闭游戏状态流，再断开游戏并重进 | 640 次流变化后仍可重连同房间，同端口保持可用，真实 P2P | 原生 EXE/DLL 回归 |
| G08 | 房主关闭房间；各受邀者检查状态 | 所有人明确收到房间结束，旧邀请码不能继续使用 | 原生混合连接回归 |
| G09 | 四人保持连接，后台每 5 秒刷新好友；期间隐藏/打开窗口，重复操作 | 入口、联系人不消失；没有挂起的加载、一直协商或连带断线；记录实际持续时长 | 四游戏 soak + 点击回归 |
| D01 | 故障后导出诊断包，重启后再次导出 | 包含故障前后时间、请求/认证阶段、状态重置与恢复；不包含个人码、密码或私钥 | 已有诊断导出/留存回归 |
| W01 | 在两台以上、不同运营商/网络类型下重复 G01/G02/G06/G09 | 记录真实 NAT/路径、错误和耗时；不能用本机结果代替公网通过 | 公网环境专项，另行记录 |

快速回归通过后仍应做至少 1800 秒的保持测试。任何“全部公网环境均解决”的结论，都必须有相应网络环境证据；本地四客户端不能证明这一点。

## 故障定位日志

新增事件包括 `social_profile_read_failed`、`social_identity_reset`、`social_ui_sync_failed`、`social_ui_sync_recovered`、`social_access_expired`，写入现有 `hookup.social` 连接日志，沿用七天留存和诊断导出。它们记录失败来源、连续次数、已有联系人数量、入口状态和读取异常类型；不记录接入码、私钥、联系人 ID 或配置正文。网络根因仍须与原生请求 trace、认证拒绝类别、节点日志对齐，不能由“联系人保留”推断网络已经修复。
