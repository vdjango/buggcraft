# 网络行为探测与节点诊断上传

2026-10-30 更新问题反馈交互。源码及本地验收通过，启动器验证包未公开发布。

## 玩家使用

联机大厅和房间的入口统一为「反馈问题」，本地「导出日志」继续可用。通过节点地址和浏览器登录账号后，直接填写问题内容；首行自动生成内部标题，无需分别输入标题、描述。表单中列明收集内容、隐私范围、接收节点及受信任联邦管理员的访问范围，点击「提交问题」才开始采集上传。取消、关闭、按 Esc 或匿名状态均不会提交；草稿保留，按 Esc 只关闭表单。

表单说明自动收集系统、启动器、Java 与游戏版本、模组和资源列表、网络地址、网卡、路由、DNS、节点及联机记录、启动器与游戏日志和崩溃记录。对常见凭据字段脱敏，不打包存档、设置文件或完整 SDP；日志仍可能包含本机路径、网络地址和聊天。Native 诊断不记录转发的游戏包正文。附件供当前节点及受信任联邦节点管理员查看，并非公开下载文件。

单个 ZIP 上限 20 MiB，节点附件总存储预算 1 GiB。超过上限时明确报错，不静默删掉日志后伪称完整上传。上传成功显示反馈编号；管理员可在既有 `/admin/feedback` 页面查询、下载。失败时应先检查反馈是否已创建：中断会保留问题说明，未完成的 `.part` 文件会清理，用户可在节点反馈页补传。问题关闭后的删除与联邦同步沿用既有反馈系统。

## ZIP 中的证据

| 文件 | 作用 |
| --- | --- |
| `p2p-sessions/network-*.json` | 建连时后台采样及导出时新采样：接口、路由、DNS、IPv4 映射/过滤观察、IPv6 UDP 探测和失败原因 |
| `players/*/*.jsonl`、`*.events.jsonl` | 每次 ICE 候选端点、候选类型、地址族、选中对、尝试编号、失败/回退/心跳及游戏流路径与字节计数 |
| `p2p-evidence.json` | 去重后的会话、选中 IPv4/IPv6 对、P2P/中转流、双向数据观察和失败摘要；兼容旧日志字段缺失 |
| `diagnostics.json` | 文件字节数/SHA-256、缺失/跳过/读取失败、启动器版本、Native 刷写健康与当前运行 EXE/DLL 的 SHA-256 |

网络探测在工作线程运行，不作为开始联机的前置条件。并发建房采样采用单任务锁，跳过时记录原因；导出仍单独采集新快照。路由命令超时 8 秒，DNS 每项限时 0.8 秒，UDP 探测共用最多 16 秒预算。失败保留状态与原因，不伪造为某种 NAT 或“网络不支持”。

默认 IPv4 探测目的端为已实测可用的节点 STUN 地址 `81.68.225.236:3334`、`43.241.50.19:13331`。过滤探测解析 `stun.nextcloud.com:3478`，仅接受公网数字地址及受控替代端口；配置有全局 IPv6 时另解析 `stun.l.google.com:19302` 验证 IPv6 UDP。目的地址、回复来源、事务校验、映射、超时、重试次数及往返耗时均保留。DNS、服务或端口失效会得到未知/未证实，不能由此断言 UDP 被运营商封锁。端点未来变化应同步更新默认配置。

## 如何判读

1. 同一 IPv4 UDP socket 对两个不同服务端 IP 得到相同公网 IP/端口，记录为 `mapping=endpoint-independent`、`confidence=observed`。映射变化记录目的相关或多出口可能，不直接贴“对称 NAT”标签。
2. 过滤测试使用新 socket，先请求从尚未主动联系的替代地址/端口回复，再主动联系该端点，最后重复 CHANGE-REQUEST 验证服务端确实支持。不把单次超时当分类结果。服务缺少能力、控制失败或预算不足时为未知。
3. 只有同 IP、不同端口的服务无法完整区分 EIF/ADF；成功的前后控制可以观察端口相关过滤，但标记 `full_rfc5780=false`、范围为“主机防火墙和 NAT 的组合路径”。`port-restricted-cone-observed` 是兼容名称，不是对全部运营商设备的确定分类。
4. NAT/UDP 探测不能单独证明与任意另一玩家能 P2P。`p2p_capability` 始终明确网络探测未验证对端可达；还要看双方同一 `attempt` 的候选、信令、选中对与实际游戏 `game_path`/字节。文件 P2P 与游戏 P2P 分开核查。
5. `peer_selected_pair` 证明那次 ICE 连接；`game_path=p2p` 配合该流双向字节才是游戏数据证据。汇总不会把中转字节、只有选中对、混合路径或字段不完整的记录判成 P2P 数据成功。局域网/同一 VM 主机的成功不能冒充公网双 NAT 验证。

## 上传实现与版本要求

`utils.feedback_upload.submit_diagnostics(..., consent=True)` 再次检查同意，先生成现有脱敏 ZIP，随后单独启动 Native EXE 调用 `feedback.submit`。独立进程避免大文件上传串行阻塞活动房间的共享桥 RPC；最终退出并清理临时 ZIP。标题、描述有字符和 UTF-8 字节上限，遵守原生控制帧 8 KiB 限制。

原生桥用个人账号和固定节点公钥建立 SSH，调用 `buggcraft-feedback-upload-v1`，分块发送文件并校验节点回执的反馈编号、字节数及 SHA-256。节点再次检查账号、明确同意、大小、配额和元数据，写私有临时文件后沿用既有签名反馈事件及附件存储。匿名接入码不可上传。

需要同时发布新的启动器 Python/QML、完整 Native 运行目录，以及节点 `web/tunnel/feedback_native.py`/`directory.py`。旧桥不含 `feedback.submit` 会提示更新，旧节点不含该 SSH 子系统不能接收此上传。不能只更新 Python 文件却继续携带旧 EXE/DLL；同版本号的不同构建通过诊断指纹识别。本次已更新相邻原生仓库的本地 `runtime`，没有替换线上运行文件。
