# 好友刷新与直连故障诊断

2026-10-28 的网络行为主动探测、P2P 数据汇总与经用户确认的节点反馈上传，见[网络诊断与上传](网络诊断上传.md)。这些新增功能尚未线上发布；历史 beta.17 日志无法补回缺失字段。

beta.17 已包含大厅「导出日志」、每玩家 Native JSONL、ICE 状态及候选统计、选中候选对、信令尝试编号、重试与回退原因、心跳，以及本机网卡/路由/DNS 快照。

本次尚未发布的补强增加好友请求与 Native RPC 的关联记录，并在 `diagnostics.json` 中记录启动器版本和 `diagnostic_schema: 2`。心跳阈值仍为 20 秒。排队或取消不能被当作节点失联的证据。单个玩家连接失败应限于该玩家；房主连接失败会影响依赖房主的通道，需要分别核查。

## 采集

1. 房主与出现故障的加入者使用同一版本，记录双方网络类型、故障时间与操作。无需更改防火墙或重新登录来采集。
2. 问题出现后保留当前启动器，双方各从联机大厅点击「导出日志」。即使房间没有成功建立也能导出。
3. 由维护者按同一时间、房间及玩家会话编号对照节点日志。只提供房主日志无法确认加入者是否收到了应答或选到了有效链路。

## 好友请求

日志保存在 `p2p-sessions/*.log*`。同一个 `trace` 关联以下记录：

- `social_request_start/complete/failed/cancelled`：请求操作、目标节点地址、阶段、耗时、异常类型与数字错误码；不记录目标账号、签名事件或响应正文。
- `native_rpc_queued/complete/failed/cancelled`：方法、RPC 编号、`queue_ms` 与总耗时。排队阶段尚未发给桥接组件，不能按节点网络耗时判断。
- `native_bridge_reset`：底层读写异常、取消或超时触发的桥接重置。需要对照是否同时影响其他房间。
- `social_credential_expired/invalid`：本地个人码校验失败。过期时间以本机时钟为准，需结合节点认证结果。

`stage=node_handle` 表示桥接启动或注册节点阶段；`node_request` 表示调用节点操作；`response` 表示返回值检查。Native `phase=bridge_call`、`response` 分别标出调用与响应检查阶段。`-32031` 对应节点认证失败，`-32030` 对应节点身份校验失败；通用 `-32000` 仍需结合 Native 与节点记录细分原因，不能凭一个错误码断言运营商封锁。

正常轮询的起止记录为 DEBUG，只在联机会话日志中开启；失败为 WARNING，取消单独记录。不会记录完整请求、令牌、个人码、房间口令或签名。

## 直连协商

`players/*/*.jsonl` 中检查 `peer_stun_servers_ready`、`peer_candidates_ready`、`peer_answer_received/ignored`、`peer_ice_state`、`peer_failure_details`、`peer_selected_pair`、`peer_retry_*`、`peer_fallback` 和 `game_path`。文件传输另有 `file_peer_*`，应与游戏链路分开判断。

用双方同一次 `attempt` 区分：候选尚未收集、信令没有到达、应答过时、ICE 检查失败、已转中继、已选定直连但界面仍未更新。节点保存信令转发事件，可用于确认转发是否发生。本机四客户端测试通过不能代替故障公网环境的记录，也不能由一次 STUN 映射确定完整 NAT 类型。

Native 尚未发布的补强为 `players/bridge/runtime.jsonl` 的 `webrtc_warning` 增加 `warning_schema: 1`、`component`、`reason`、`level`、源码行号及可解析的数字系统错误码。可区分 STUN DNS/发送/校验、ICE 候选/超时、DTLS 握手和 SCTP 发送等错误。未识别的警告保留固定的 `unclassified` 分类、组件与长度，不保存原文，因为 libjuice 的警告可能直接包含 ICE 密码、用户名及候选 SDP。

WebRTC 回调是进程级别，`scope=runtime` 不代表某个玩家或某次协商。应结合时间及双方 `peer_failure_details` 判断；同时有多个房间或独立文件通道时，不能把一条全局警告强行归到某个 `attempt`。旧日志中只有事件名的 `webrtc_warning` 无法事后恢复原文，也不能据此推断具体网络封锁。

## 节点错误与共享桥接生命周期

实际好友刷新路径为 `refresh_friends → social.status/operate → NativeRoutes.handle → social.operate`。当前源码及 beta.17 发布提交 `74a5373` 中，没有生产调用方调用 Python `choose()`/`ordered()`。此前人工调用 `choose()` 得到的桥接关闭现象不能解释这次真实故障；围绕该假设增加的整体关闭、桥接代次和提示改动已经撤回，未部署。

节点选路有两种：目录请求选择后续使用的节点，已有房间不会因此迁移；单个房间自己的 SSH 失效后，该房间重连时尝试备用节点。Native `Session` 独立保存连接资料、线程和 SSH，服务端按连接编号清理相关流。玩家断开不应清理房主和其他玩家；房主断开时，依赖房主的中转流会中断，房间进入等待恢复状态。

共享桥是同一启动器内的 DLL 实例或 EXE 进程，不是所有远端玩家共用的服务器连接。完整返回的节点错误不会触发 `handle()` 或 `social.operate` 关闭共享桥。真实存在的整体关闭入口是启动器与本机桥交换中断、交换超时或协议损坏，以及启动器退出；历史日志尚未证明此次故障发生了本机桥交换重置。排队等待不计入 45 秒交换超时。

传输超时、交换中断、无效 JSON、响应编号不符也会关闭桥，以免后续请求误读旧响应。`-32031` 不能直接解释为接入码过期：房间关闭、人数上限、重复房主或无效凭据都可能在 SSH 认证阶段被拒绝。个人码通常有效 7 天；到期本身不会使一条已经认证的 SSH 连接变成心跳超时。历史故障中未发现认证拒绝记录。

客户端回归入口为 `tests/test_native_bridge_runtime.py` 和 `tests/test_native_bridge_services.py`。前者通过实际 DLL/EXE 验证完整错误响应不销毁共享桥、并发请求和关闭重启；后者在独立子进程中使用原生仓库的实际节点、房主与加入者，验证接入码、完整模组清单、禁止中转传文件时游戏仍可收发、聊天与社交签名。可设置 `BUGGCRAFT_NATIVE_SOURCE` 指向已编译的原生仓库；其管理层依赖只存在于测试进程。原先依赖旧 `tunnel` 导入的客户端 live 用例已移除，目录认证被拒绝、握手超时及取消期间的跨房间故障隔离不能凭上述用例标成实测通过；需补充独立原生场景。Native 心跳测试另验证单个受邀端黑洞时，同房主的另一玩家保持工作。人为制造的错误验证隔离范围，不证明历史事故也发生过这些错误。

## SSH 心跳与底层断开

客户端 `heartbeat_timeout`、`endpoint_disconnected` 和节点 `disconnected` 增加 `transport` 数值快照：`rx_age_ms` 是最后收到 SSH 包到检查的间隔；`poll_gap_ms`/`max_poll_gap_ms` 是心跳检查间隔；`probe_attempts` 是尝试调用探测的累计次数，不等于已发到网络或已收到回复的次数。另有 SSH 状态、错误码、包数和字节数。节点控制 RPC 超时单独标为 `control_rpc_timeout`，不再混作传输关闭。

心跳持续被检查、收包停止与检查线程长时间未运行会产生不同的间隔数据。`ssh_error_kind` 仅使用固定分类，区分 EOF、连接重置、系统超时、SSH 远端断开和包完整性失败；不输出底层原始错误文本或远端断开说明。原始文本可能包含凭据。此处不读取 `SO_ERROR`，避免诊断代码清除套接字的待处理错误。

旧日志未采集这些字段，不能事后填补。2026-10-26 上海房主连接失效期间，同房间另一个玩家仍持续进行控制请求；同房间连接在节点分配给同一个工作线程，这不支持整个工作线程长时间停顿的解释。仍需包含新增字段的双方及节点日志，区分房主网络链路与客户端连接处理失败，不能仅凭服务端心跳超时断定其底层原因。

## 日志留存与导出完整性（2026-10-27，尚未上线）

客户端和节点的事件增加 `process_id`、递增 `sequence`、`monotonic_ms`、`journal_dropped` 和 `journal_write_errors`。单调时钟仅用于同一系统内判断间隔，不应用于跨机器时间比较。重启后的进程编号、会话编号及序号要一并核对。

关键事件同时保存到独立的 `*.events.jsonl`，另有一个 `.events.1.jsonl` 轮转文件；高频采样只写普通日志。队列已满时，关键事件优先挤出普通采样，普通采样不能挤出关键事件。若关键事件本身填满队列，仍可能丢弃，但会增加计数。普通采样最多使用总预算的 75%，其余空间为关键事件留出余量，达到总预算仍会删除旧文件。

| 范围 | 默认留存策略 |
| --- | --- |
| 启动器 `p2p-sessions` | 启动时清理超过 7 天及总计 128 MiB 的旧会话/网络快照；当前会话每文件 10 MiB、8 个备份 |
| Native `players` | 7 天、总计 256 MiB、最多 4096 文件；普通及关键事件文件分别 4 MiB、各 1 个备份 |
| 节点 `logs/players` | 7 天、总计 1 GiB、最多 5000 文件；普通文件 16 MiB、关键事件文件 4 MiB，各 1 个备份 |

这里的 7 天是按文件修改时间清理的上限，并非容量不足时仍能保证保存整整 7 天。清理在后台周期执行，预算不等于每次写入都同步检查的硬限制。连接头随节点文件轮转保留，断开并重启服务后仍能查到会话。管理端 `events` 时间线会合并独立保留的关键事件并去重，原有管理界面与导出不会遗漏这些事件。

SSH 新连接失败记录 `ssh_connection_failed`，包含 `connect`、`identity`、`authenticate` 阶段、角色和数字认证返回码。节点对认证拒绝记录固定原因：账号记录不可用、封禁、签名校验失败、过期声明、房间已满/不存在/关闭、重复房主等。`account-expired-claim` 是校验走到过期条件，不能作为该凭据的签名已验证的证明。每连接最多保存 3 次认证拒绝，且用任务上下文隔离并发认证的原因，避免串到其他玩家。

节点每次刷写更新 `journal-health.json`，记录丢弃、写盘失败及待写事件计数。EXE 的固定存储失败告警会进入启动器联机日志；其他原始 stderr 不复制，以免泄露凭据或 SDP。DLL/EXE 均可通过新增的 `bridge.diagnostics` 读取计数和队列刷新结果。

大厅导出在联机事件循环上先请求 Native 刷新队列（最多等待 2 秒），再在工作线程打包。桥忙、版本不支持、未运行或收集失败时，`diagnostics.json.native_journal` 明确标记 `busy`、`unsupported`、`not_running` 或 `failed`，不会伪称队列已刷完，也不会为导出启动一个新桥。导出时关键事件优先；超过 200 MiB、缺失和读取失败的文件均在清单中标明。`flushed=true` 表示队列已处理，仍需检查 `write_errors`；它不代表没有丢记录。

故障发生后，应在当前启动器中尽快导出房主和受影响加入者的 ZIP，同时保留对应节点的普通日志、关键事件及 `journal-health.json`。凭据、个人码、房间口令、游戏正文及原始错误文本不作为诊断内容保存。新增证据可区分已覆盖的故障阶段，不能保证所有未知公网问题都无需进一步复现或抓包；历史缺失的数据无法补回。
