# 联机控制报文故障与打包回归

2026-11-17。本次修复对象是最终 Windows 单文件启动器的“联机引擎不可用”，不以开发目录里的独立桥接程序替代交付程序。

## 故障与修复

实际运行的 26.3 世界，服务器状态携带约 14 KiB 的 favicon。此前服务器列表信息改动把 favicon、描述、模组信息和完整玩家样本加入 `game.discover` 返回值；启动器建房/重定向又将该对象作为控制参数发送，超过 NativeBridge 现有 8,192 字节上限。原校验将超限、关闭中、排队满、文件缺失统一显示为“联机引擎不可用”，掩盖了真实原因。

本次保持原 8 KiB 控制限制：原 `modern_status` 只返回端口、64 字符以内版本、协议号、在线/最大人数、探测延迟五项。多人游戏列表通过原状态流接收服务器图标、富文本和模组信息，控制请求不携带这些大字段。未提高限制来容纳无关图片。

`NativeBridge::call` 保持原队列、优先级和异步回调，按关闭中、32 项队列已满、请求超限、文件缺失分别给出原因；`bridge.rejected` 仅记录方法、原因、字节数和队列长度，不记录凭据或整个请求。析构断开 QProcess 对自身的回调，避免异常测试退出时成员队列已销毁仍被进程结束信号访问；正常退出继续使用原 shutdown/drain。

检索并复用：`modern_status`、`MultiplayerService::create_room/connect_world`、`NativeBridge::call/shutdown`、原 GameStatusServer、单文件构建脚本和现有网络集成夹具；没有新增联机服务或第二套状态通道。

原生控制流程在 WSL Linux 原生服务/隔离 PostgreSQL 与 Windows EXE 之间运行。首次复跑遇到 WSL 到 Windows localhost 转发尚未就绪；夹具现先从 Windows 验证实际端口可达，再发起登录，不改产品网络信任或放宽断言。最终通过记录对应修复后的单文件程序。纯测试工具可以使用 Python，产品联机仍为 C++。

新增两项行为回归分别覆盖：20 KiB 图标、长描述、500 模组和玩家样本不进入控制报文；超大请求、满队列、关闭和缺失文件可区分且不会破坏后续 RPC。现有静态构建测试统一使用交付的 `bugg.exe --native-bridge`。单文件打包默认构建测试，并在安装/打包前执行 `packaged_multiplayer` CTest；GitHub 工作流显式启用该门禁。本次没有触发 GitHub 发布，远端 CI 运行结果不在本地验收范围内。

## 交付与边界

最终程序同步原入口 `build/bugg.exe`，与静态构建产物 SHA-256 一致，摘要见 build/verification/engine-repair-artifact.json。没有替换用户正在运行的 E:/bugg/bugg.exe，也没有终止用户的游戏。

这些证据覆盖明确列出的 Windows 路径，不等于“全部用例全面覆盖”。macOS/Linux 图形界面、多台真实外网设备穿透、所有模组组合、千人并发与长时间运行没有在本次得到完整实测，不能标为通过。源站完整下载与尾段性能另外记录在源站第 66 号文档，不能以局部接收函数测速代替整个缓存流程。
