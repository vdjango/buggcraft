# 下载链路性能分析与实施方案

## 2026-11-17 房间同步与并发稳定性追加结论

这次确认的等待来自实际串行代码：房间每个文件各请求一次 resolve、各执行一次 fetch，P2P 也逐个等待。现改为本地摘要复用、每次最多 300 个哈希批量解析、公共文件合并并发下载、未完成文件并发房间传输；仍复用 ResourceClient、RoomContentCache、原生桥和原子提交，不引入第二套下载器。源站解析查不到时使用公开地址、短预算公开目录查询和 P2P；不等待源站先把整个文件缓存完。

可选目录补全给整批 2.5 秒预算，到期取消剩余查询，保留已找到的结果；单个 404 不丢掉其他文件的成功结果。该预算不随文件数量相乘，必需安装元信息不套用可选查询的容错规则。

Modrinth 的目录 API 与 CDN 文件也需要镜像和官方候选，而不是仅优化 CurseForge。参考代码对这两类地址使用独立镜像域名替换，文件仍交给共用下载器；没有一个仅靠改 CDN 名就保证 10 MB/s 的特殊通道。BUGG 适配器已将 `api.modrinth.com/v2` 接到 `/v1/catalog/modrinth`，`cdn.modrinth.com/data` 接到 `/mods/modrinth/data`。房间现在同时提交 SHA-256/SHA-1，使源站只有 SHA-1 的跨平台记录也能被利用，并按完整摘要确认候选确为同一文件。Modrinth 仍保留已测较优的 HTTP/2 单文件方式，多文件照常并发；CurseForge 保留已测的 HTTP/1.1、有界 Range 队列与双 CDN 候选。第三方镜像不作为未经测量的默认依赖。

| 所有者 | 本轮行为 |
| --- | --- |
| 启动器 HttpClient | 所有 worker 的 HTTP 和 Range 子请求共享进程 64 个网络槽，FIFO 授予，取消/销毁释放 |
| 启动器 ResourceClient | 文件并发沿用设置；Range 按竞争文件数分配，单独大文件仍可用满预算；批次故障源即时切换，下一批重新尝试，不增加计时等待 |
| 房间同步 | 公开文件组成一个批次；桥同时保持最多 min(设置并发,16) 个文件传输；主进度汇总完整清单且不倒退，最终校验/提交前最多 99% |
| 源站 | 保留 max_serving、月流量和带宽保护；可信公开文件繁忙即 307，未映射私有文件即时失败供客户端走房间传输；不让玩家等待缓存准备 |

源站后台回源另已移除按单次 403/429/503 自行计算整域停用的规则。错误未声明 Retry-After 时立即沿原 alternate_download 尝试备用来源；明确上游限流仍遵守，避免扩大重试风暴。旧人工期限不恢复，后台字节任务和网络池仍有界。这些追加源码没有混入单方法部署授权。

本地 Windows 回归验证了进程总量、503 即时切源、批次故障共享、房间实际多文件启动和原子发布。源站突发 1000 个请求全部重定向到已验证地址且没有占用额外文件槽；这是受本地 aiohttp 调试模式和客户端连接池约束的逻辑回归，不是生产 1000 用户容量或延迟保证。保留扩展回归的失败记录；旧的纯文本 JAR 和旧配额测试夹具对齐真实输入后通过，没有修改生产校验来掩盖失败。

## 要回答的问题

当前机器物理网卡协商为 100 Mbps，理论线速为 12.5 MB/s；实际有效负载还需扣除协议开销。目标是查明为何同类资源存在数十 KiB/s 与约 10 MB/s 的差别，并验证持续速度、完整性和失败恢复，不能只截取瞬时峰值。

源站所见 200–400 KiB/s 是服务器所在网络、特定探测对象和采样窗口的结果，不是客户端全部连接的吞吐上限。同样，多个文件的合计速度不能直接与一个文件的一条连接比较。实测须分别记录 MB/s（十进制）和 MiB/s（二进制）。

## 已核实的实现差距

- 原生文件下载共用 `ResourceClient → HttpClient`；游戏核心、库、资源、加载器、内容和整合包不需要另造下载器。不同资源组已能同时推进，资产索引完成后会展开资源文件，无需等整个游戏核心下载完毕。
- 现有大文件固定 3 段，且要求已知大小和 SHA-1；只有小文件并发设置并不能保证一个大文件能充分利用网络。已有非空续传文件仍走普通续传，这与冷下载的路径不同。
- Qt HTTP/1 默认同一主机最多 6 条连接；逻辑上发出更多请求，可能只是进入 Qt 内部等待。HTTP/2 则可能在一条 TCP 连接上复用，不能把请求数等同于物理连接数。依据：[Qt 6.8 QHttp1Configuration](https://doc.qt.io/qt-6.8/qhttp1configuration.html)。
- 只有扩大分段而没有整体预算，会使多个大文件的连接数相乘。应保留资源组独立推进，同时限制真实传输请求数、给新文件留位置，避免几百个连接及无限重试。
- 来源映射集中在 `resource_urls`，但现在有较长的按域名分支。来源能力登记已有 BUGG / BMCLAPI / 官方及缺项补齐，应在这个所有者内拆分适配器，不能把 URL 规则散落到安装流程。
- CurseForge 的 edge 与 mediafilez 对同一文件可能返回不同状态。已测一个真实文件：源站转到 edge 后 404，mediafilez 返回正确 206。换地址解决可用性，不证明可以达到 10 MB/s。

## 全链路范围

进一步审计后的调度结论：并发上限应属于共享传输器，先让等待的文件开始；整体吞吐不足时再把预算补给大文件。分段要能从失败位置恢复并逐步缩小剩余工作，不能开局固定几等份后一直等待最慢一份。已审计的实现包含全局连接计数、动态低速基线、约 256 KiB 的最小可拆余量、从最大剩余片段后部拆出约 40%、持久 HTTP 客户端、流式读取，以及核心/库/资源的依赖任务图。它们共同起作用，没有发现一个可替代所有调度与校验的特殊域名参数。本轮独立扩展既有 Qt 实现，没有移植外部下载器代码。

当前产品选择更简单的有界小分段队列，而没有复刻完整动态区间链表：优先解决已实测的慢连接、整文件重试和落盘开销。房间追加修复已实现进程级 FIFO 请求预算；按实时吞吐动态扩缩连接尚未实现，不把它写成已交付能力。

| 类别 | 元信息与身份 | 可并行的工作 | 必须等待的工作 | 实测要求 |
| --- | --- | --- | --- | --- |
| 游戏核心 | 版本 JSON 的下载 URL、大小、SHA-1 | client JAR 与库、资源文件 | 安装处理器需要的核心完成 | 完整 JAR、摘要核对 |
| 游戏库和 natives | libraries/artifact/classifiers | 不同库同时下载，完成一个补一个 | 处理器所需的库与 natives 解压 | 真实文件组合、总吞吐和尾部耗时 |
| 游戏资源 | assetIndex 与对象哈希 | 索引完成立即展开对象，与其他组重叠 | 每个对象需拿到索引中的身份 | 小文件和大对象组合，不能只测一个对象 |
| Forge / NeoForge | 安装器、安装配置、Maven 坐标 | 已知库可与原版文件并行 | Java 处理器及其声明的输入 | 安装器和库；下载与处理耗时分开 |
| Fabric / Quilt | 元信息、profile、Maven 库 | profile 解析后库文件并行 | profile 获取与校验 | 两种加载器都走同一下载机制 |

| 模组及依赖 | 两平台文件元信息、真实包内事实 | 批量查询及各文件传输 | 有关依赖决策和事务提交 | 大小模组、同平台多文件 |
| 光影包 / 资源包 | 发布文件大小、摘要和地址 | 与模组、游戏文件重叠 | 完整校验后安装 | 大文件连续速度与整段校验 |

| Java / 启动器资源 | 官方清单及摘要 | 与不依赖它的下载重叠 | 需要 Java 的处理器 | 使用同一取消、落盘与校验机制 |

## 测量方法

使用 C++ 测试入口调用同一原生 HTTP / 资源下载实现；测试入口不进入产品运行链路。输入保存实际 URL、发布者大小与摘要。下载目录每轮独立，避免本地命中；上游 CDN 缓存状态不可控制，如实记录。

大文件至少覆盖数百 MiB 的真实整合包和完整游戏核心；对同一文件比较单连接、现有分段和较高并发。每秒记录累计接收字节，输出 5 秒窗口速度、启动耗时、全程均值、稳定阶段分位数、最长停顿、尾部耗时、失败及完整 SHA-1 校验。过慢基线允许在明确的观察时限取消，但必须标成“未完整下载”，不得算成功。完成的轮次必须校验完整文件。

高连接数只是实验变量，不能先承诺 64 条更快。HTTP 429 / 403 / 503、Range 拒绝、超时和 SHA-1 错误都保留在报告中；不通过换子域名绕过平台限流。单文件与多文件测试分开，测量轮次不同时占用链路。

此前 3 MiB 前缀样本只用于确认 Range 可用性：单连接约 69–97 KiB/s，3 连接约 155–207 KiB/s，6 连接一次失败、一次约 280 KiB/s。它不构成大文件稳定性结论，原始记录在 `build/verification/cf-slow/epic-range-baseline.json`。

## 实施职责与顺序

1. 先完成 C++ 大文件和各类真实资源基线，确定连接池、分段、源选择与尾部拖慢分别占多少时间。
2. 启动器：在唯一 `HttpClient` 调整有界 HTTP 连接池与分段机制，在 `ResourceClient` 管分组调度、候选回退、完整校验和取消。不能为整合包、模组再写专用下载器。
3. 来源层：复用 `download_sources` 的能力计划，把每个源的 URL 映射集中到单独 `.h/.cpp`，统一注册；调用方只传资源和来源设置。BMCLAPI 不支持的模组/整合包由已登记的补齐源处理，不构造不存在的 BMCLAPI 下载路径。官方 CurseForge 元信息需要授权时仍经已配置源站获取，不能因补齐直接失去元信息入口。
4. 源站：命中直接传实体，未命中立即给可用的候选地址并后台缓存；不让玩家等缓存完成。服务器探测用于服务器回源选择，客户端实际表现用于自身回退。若实测暴露源站返回失效候选或 Range 错误，修改其唯一路由所有者，不把调大后台缓存并发当成客户端提速。
5. 改动后同样本复测，并执行分段拒绝回退、摘要失败、取消不提交、不同资源组并行和 BMCLAPI 内容补齐测试。确认后同步本地固定启动入口；本轮不自动发布或部署。

### 根据测量进入实现

采用有界小分段队列，完成一段立即补位；短暂失败只重试该段，保留已完成分段。每个文件和每个客户端均有连接预算，不能把 64 乘以所有大文件。CurseForge 大文件实测 HTTP/1 独立连接更快，协议策略限制在已测传输场景，不全局禁止 HTTP/2。校验仍为准确 Content-Range、总大小及发布者完整摘要，不能用放宽校验换速度。

来源接入通过一个纯值接口 `ResourceSourceProvider::urls`，每个来源单独 `.h/.cpp`，统一注册。`ResourceClient` 只组合能力计划与候选，不再拥有一长串来源 URL 分支；BMCLAPI 内容能力缺失时使用已有补齐规则。元信息鉴权和文件直连是两件事，不把它们混为一个失败。

## 已实现的网络与性能调整

- 复用 `HttpClient::request/start_request/ranged_request/cancel`，增加客户端级真实请求预算和队列。每个客户端至多 64 个活动网络请求，不是每个文件另开 64 条而无限相乘；不同独立安装任务仍各有自己的客户端，未声称进程级总上限。
- 64 MiB 以上已知摘要/大小的大文件使用约 512 KiB 小分段，完成立即补位。先确认首段精确 206 才扩展，不支持 Range 就回到普通 GET，并短期记忆。
- CurseForge 文件传输依据实测采用 HTTP/1.1；元信息及其他发布者继续使用原 HTTP/2 能力。游戏核心在本机单 HTTP/2 比强行切段快，不能全站机械套用同一参数。
- 短暂失败只重试受影响分段，最多三次；尾部仅在余量充分、分段无进展或持续极慢滴流时重新补位。保留完成片段，取消不能提交半文件，429 等状态交回原资源回退预算，不在分段层无限重试。
- 高频进度聚合限制在既有 100 ms 呈现节奏；完成字节累计后从活动分段表移除，避免每次回调遍历所有历史分段。任务页标注文件传输数量，不冒充 TCP 连接数量。
- `ResourceClient` 继续按资源组使用设置并发，索引一旦就绪立即展开资产对象，不等整个游戏核心结束。暂时故障先尝试下一允许来源，不在同一个坏地址反复等待。
- 来源独立为 `BuggResourceSource`、`BmclapiResourceSource`、`OfficialResourceSource` 各自 `.h/.cpp`，注册在 `resource_source_provider.cpp`；能力及补齐顺序仍归 `contracts/download_sources`。新增来源无需修改安装、整合包、模组和 UI 流程。

临时分段曾逐段调用 `QSaveFile::commit`，Qt 实现会逐段同步到磁盘，约 740 段意味着约 740 次同步。本轮进一步让私有暂存目录中的分段使用普通流式写入，只有完整目标执行一次摘要校验和原子提交。这项收益必须以最后复测为准，不能用减少同步次数推算速度倍率。未改普通文件的持久续传/原子提交契约。

## 启动器与源站的职责结论

主要提速改动在启动器，源站只是其中一个来源适配器。实测同一官方 URL 已能从低速基线提升到连续 11–12 MB/s，中段速度差异不能归因于 mediafilez 名称本身。现阶段不需要为提速另造一个源站下载协议。

源站继续承担缓存命中直出、未命中及时重定向/后台缓存、候选可用性和 Range/实体身份正确性。本轮读取其现有策略并测试实际 BUGG 下载入口，没有部署源站；服务器测到的 200–400 KiB/s 只描述服务器回源路径，不能拿它直接限制或承诺玩家速度。长期质量统计应区分服务器回源测速与玩家实际传输反馈，记录文件大小、首字节、持续吞吐、失败率、节点和时间窗口，避免很短的探测选错源。

选择 BMCLAPI 时：其支持的游戏/加载器资源先走 BMCLAPI，内容类由已有官方补齐规则处理；如果需要 CurseForge 授权元数据，继续沿可用的 BUGG 元信息入口。不会给 BMCLAPI 编造模组和整合包文件路径。

## 2026-11-17 503 稳定性修复

205.88 MB 的既有实测曾出现：BUGG 正式存储地址 503，客户端约 3.5 秒后又试同源另一路径并超时，约第 26 秒才访问官方源。源站代码将每个 Range GET 计入 `max_serving`，这是可能的准入原因；当时的 503 没有记录拒绝原因，因此不能断言它就是该次故障的直接原因。
