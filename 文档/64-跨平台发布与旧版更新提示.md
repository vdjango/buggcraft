# 跨平台发布与旧版更新提示

2026-11-16 用户报告旧版自动更新重启时 Qt 平台插件加载失败，要求更新说明提示官网手动下载，并补齐 Mac / Linux。截图只能证明该启动环境插件初始化失败，不能将前轮隔离 v1.1.0 测试推广为全部旧版兼容，也不能仅凭截图认定是游戏问题。

v2.0.1 GitHub 和下载站的发布说明已立即添加同一重要提示；实际读取 legacy / cpp 更新接口确认返回，并确认原资产摘要不变，证据 `build/release-warning-20261116.json`。

检索 `LauncherUpdateService`、`tools/package_release.py`、`package.yml`、节点原生运行库安装、Qt 官方 QML 部署 API 和主入口路径。复用原打包器、Qt 部署和原生节点桥，不复制游戏 / 更新状态机。新平台使用动态 Qt 完整目录，Windows 保持既有静态单文件；运行时没有 Python。构建期工具可使用 Python。

`BUGG_DESKTOP_PACKAGE` 仅启用 macOS / Linux 的安装规则；Mac 使用 .app，Linux 可执行文件放在安装根。`package_release.py --platform --directory` 沿同一 ZIP / 清单 / 语言附件入口处理完整部署目录。仅将包内符号链接展开为普通文件，拒绝指向部署外的链接，兼容原更新器禁止归档链接和保留可执行位的安全约束。Mac 用户数据目录在 .app 外，桥仍从程序内路径读取。

Mac framework 展平为不含链接的结构，同时修改 Mach-O 引用，禁止 `/opt/homebrew`、构建 SDK 等外部运行依赖。QML 原符号链接展开后，框架引用统一从应用可执行文件定位；否则原 `@loader_path` 的目录深度会失效。原生许可移到 Resources，先签内部组件、再签整个应用并进行严格验证。`Contents/Resources/qt.conf` 明确使用相对 `Resources/qml`、`PlugIns`、`Frameworks`；CI 临时移走 Qt SDK 后再打开程序，避免开发机库掩盖漏包。Qt 许可复用原单文件构建从相同 6.8.1 源码生成的完整文本，桥许可随已校验的发布附件保留。

下载站复用 `build_browser_packages`：Mac 为原 Contents 文件加 `Bugg.app/` 前缀，Linux 完整保留启动器、库、插件与原生桥，生成官网已有架构选项识别的 `Buggcraft-{macos,linux}-{arch}.zip`。更新 ZIP 保持不变；浏览器包装保留内容和执行位，先完成生成再进入审核发布。旧版原始程序打包和更新接口继续沿用。最终浏览器下载测试 17 项通过，包含两种 Linux 架构、Mac 应用结构、摘要校验、权限、HTTP 分片及失败回退。

v2.0.2 已在五个平台构建全部成功后统一发布，使用现有下载站完整版本导入流程，不修改已发布 v2.0.1 资产。构建与实体设备验收分别记录，未持有 Apple Developer 证书时不声称已公证。

未发布构建的 macOS ARM64 / Intel 截图成功后退出崩溃。诊断任务 43788739815 的 LLDB 完整栈定位到进程全局析构期间 Qt 输出日志，仍调用 main 安装的诊断回调，而函数静态脱敏正则已经销毁（QString::vasprintf → QRegularExpression::globalMatch → redact_diagnostic → record_diagnostic → diagnostic_message → __cxa_finalize_ranges）。修复为复用 Qt QScopeGuard，将回调有效期限定在业务服务生命周期内，早于 QGuiApplication 和静态对象析构时恢复原处理器；不关闭错误日志或泄漏静态资源掩盖问题。

本轮构建、公开页面、平台启动与更新接口证据见下方最终记录。

Linux 末轮截图发现固定 1.3 秒时仍在初始化；开发截图模式改为等待既有生命周期进入用户协议 / ready，30 秒未完成则失败，避免只验证到初始化画面。该调整只影响显式 `--capture`，正常启动仍走原生命周期。

最终五平台构建和启动全部通过后，原发布脚本使用 Windows PowerShell 5.1 上传大 ZIP 时出现 `The underlying connection was closed ... on a send`，保留未发布草稿。恢复只下载已通过任务的原始 Actions 附件，校验 GitHub artifact 摘要后流式补传并核对各附件摘要，再重跑原发布任务；不重编译、不更换已验收程序。后续同一发布入口改为 GitHub CLI 流式上传并关闭旧 PowerShell 进度开销，摘要一致的附件仍沿原逻辑跳过。版本标记在本轮不同系统分别使用 LF / CRLF，内容均为 2.0.2；后续打包显式固定 LF，避免平台合并时仅换行不同。

原任务恢复时还暴露了 PowerShell 把 REST 发布列表额外包装成嵌套数组的问题，导致草稿查找后拿到多个 URL。已修复为明确遍历记录，并将同一发布任务移到 `publish.yml`：正常打包调用它，失败恢复也调用它，避免重建已经验证的五平台程序。恢复先核对标签 SHA、原构建工作流、五个平台全部成功，再下载原 Actions 附件；已公开附件只允许摘要相同的幂等重试。正常标签构建仍通过原 package.yml 的 Actions 身份触发下载站；主分支手动恢复由下载站原定时 GitHub 同步获取，不放宽 OIDC 身份范围。

参考：[Qt 6.8 QML 部署](https://doc.qt.io/qt-6.8/qt-generate-deploy-qml-app-script.html)、[Qt 6.8 运行依赖部署](https://doc.qt.io/qt-6.8/qt-deploy-runtime-dependencies.html)。
