# 广场与内容体验验收（2026-11-10）

## 最终行为

广场入口仍为四类内容：模组、资源包、光影包、整合包。去掉重复的大标题与导入整合包按钮；整合包拖入窗口沿用既有导入。搜索与平台在同一行，下方仅保留“筛选 · 游戏版本 · 加载器 · 分类”和结果数量。默认收起，点击展开目标游戏、版本、加载器和内容分类；960 常规窗口四列，410 悬浮面板两列，同一页面与控件，不另建小窗口实现。展开状态和目标保存在原页面草稿中。

初次进入按当前实例自动匹配版本与加载器，用户可以修改筛选；修改搜索条件不偷偷切换真实安装目标。不同平台、内容类型使用各自实际分类。详情以作者的图文介绍为主要区域，常规右侧为安装表单；悬浮面板用“介绍 / 安装”切换，同一 ContentInstallOptions。元数据查询显示“搜索中…”或旋转等待，不使用假的下载进度条。正文独立滚动，安装按钮不覆盖阅读区域。

模组写入目标实例 mods，资源包 resourcepacks，光影包 shaderpacks；整合包使用新名称创建独立游戏。实例内“模组与资源 → 在线添加”携带目标进入同一目录。没有模组加载器时显示创建兼容游戏的引导，预选游戏和加载器，经原安装队列创建后安装所选内容；不要求用户自行猜测版本。

## 必要依赖与失败语义

ContentProvider 唯一解析器只自动处理 required，optional 不隐式安装，重复依赖去重，版本冲突/不兼容依赖记入 missingDependencies。根内容自身不兼容、无可信可校验文件时仍拒绝安装；不能把“所选模组安装成功”解释为忽略主文件错误或允许不兼容文件。

安装先校验、提交用户选择的主内容，再逐个复用原文件事务补齐依赖。某个依赖的查询、兼容、冲突或安装失败不回滚已成功的主内容；任务明确显示“待补齐依赖”、名称、原因，并提醒游戏可能无法正常运行。点击“重试依赖”重新解析元数据并补装，沿用原任务、取消与持久化；创建兼容游戏的完成任务补装时使用原实例，不再创建重复游戏。

健康计划不重复请求依赖元数据；只有已有未解析依赖或补装重试才重新查询。下载仍为 ResourceClient/HttpClient，摘要和路径验证、显式替换、单事务失败回滚不削弱。取消保持取消语义，不将取消任务冒充完成；已经提交的主内容会保留。

## 检索、复用与边界

已检索旧版 core/content.py、curseforge.py、content_mirrors.py，以及新版目录 Session/Provider、GameRuntime.install/retry_task、GameOperations.install_content/commit_content、文件摘要与原队列。缺少的是真实分类、图文归一化、兼容引导和依赖部分成功语义；扩展原所有者，没有新增下载器、队列、来源设置或 Python 运行依赖。

content_description 在 catalog worker 复用 QTextDocument 生成 html/image 块。真实 Round Trees 正文以 center/details 等 HTML 容器开头，Qt 6.8 Markdown 导入会丢失内容，修正为识别 HTML 文档并复用 HTML 导入；Markdown 链接图片的 anchor 在 Qt 6.8 被丢失，仅有界提取该链接元数据，正文仍交 Qt 解析。RichDocument 虚拟化，ContentImage 复用 Qt 异步图片加载。链接图片为最多 220 px 的小预览，可点开原链接；普通截图占正文宽度，避免赞助徽章把正文挤出首屏。

筛选复用 SummaryButton、SelectField、NavigationBar、PageStateStore；弹层坐标在真实打开及尺寸变化时重算，修正筛选折叠后菜单跑到窗口左上角的问题。详情安装选项唯一实现，任务提示扩展原 TaskCard。接口与索引同步到 12、16、17、18、22 文档。

## 性能约束与可复现实测

Windows x64、Qt 6.8.1、MSVC Release。本轮无全局 SIMD 编译选项变动，继续保留 Windows/macOS/Linux x64/ARM64 基线；未在 macOS/Linux 实测。列表每页 20，依赖最多 128，正文截取 256 Ki 字符、正文图片 32、画廊 12；图标解码宽 96、插图宽最多 1024。缓存最多 64 项 / 8 MiB、5 分钟，来源变化失效。网络、正文解析、文件安装均在原受控 worker；GUI 不读文件和解析远端文档，不新增空闲轮询线程。

`content_test query_cache_measurement` 同机器/构建、同 HTTP fixture、固定 15 ms 响应延时，七组冷查询与暖查询。14 次查询只发 7 次 HTTP。最终冷查询中位 **20.2635 ms**，范围 19.2433–20.9252；暖查询中位 **0.0231 ms**，范围 0.0207–0.0254。原始样本在 `build/verification/content/cache-report.json`。这衡量已实现的查询缓存收益，包含模拟延时，并非新增 UI 修改带来的整体加速，不外推公网或其他平台。现有用户启动器与 IDE 未关闭，测量并未隔离系统后台负载。其他既有性能工作见 27–29 文档。
