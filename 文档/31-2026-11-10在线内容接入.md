# 在线内容接入与验收（2026-11-10）

## 使用入口与最终行为

广场共用“模组 / 资源包 / 光影包 / 整合包”目录，支持搜索、CurseForge/Modrinth 切换、按目标实例过滤游戏版本及加载器、结果与版本分页。项目详情选择兼容版本后显示必要依赖，目标预检结束才能安装。已有不同内容或旧版本需要确认替换；下载及校验结束前不改原文件，提交失败恢复备份。

实例 → 模组与资源 → 在线添加，携带当前实例及内容类型进入同一个目录。模组写入 mods，资源包写入 resourcepacks，光影包写入 shaderpacks；原有本地添加、启停和删除保留。安装游戏页顶部“查找整合包”也进入同一目录。整合包填写新名称，经归档校验后调用现有 import_pack，创建独立实例，不覆盖已有游戏。

任务继续使用 GameRuntime 的持久队列、进度、取消与重试。正在运行的目标实例拒绝修改；恢复的排队任务也会再次核对。安装完成刷新实例及本地内容快照。

## 检索与复用

先检索旧版 core/content.py、curseforge.py、content_mirrors.py 的分类、依赖、地址及归档格式，再检索新版目录端口、任务、来源、网络、摘要、导入和本地管理。缺少的是在线元数据适配，新增 catalog 的 ContentCatalogService/Session/Provider；没有复制下载器、任务队列或游戏安装器。

沿用 SourceSettings/resolve_sources、HttpClient、ResourceClient.fetch/resource_urls、GameOperations.import_pack/commit_content、GameRuntime.install/run_file_work、PageStateStore 和 DesignSystem。copy_file、validate_content_record、verify_content_file 从原私有方法提升共享，本地添加、迁移、房间、整合包及在线安装共用。SearchPage 已删除；广场和二级目录复用同一个 CatalogPage Component。

CurseForge 使用旧版已存在的 BUGG 公共网关；官方凭据仍按既有环境配置读取。Modrinth 元数据沿用官方接口，文件优先级仍归现有下载来源。不添加客户端测速回退或第二套来源设置。

## 功能验证

原生 Release 编译、all_qmllint 和 qml_component_boundaries 通过。CTest 的 sessions、catalogs、content、runtime、qml_component_boundaries 五组通过；UI 的语言四种尺寸、游戏版本选择器、跨页面草稿三项回归通过。日志位于 build/content-final-build.log、content-ctest.log、content-ui-regression.log。

## 性能约束与实测范围

实现时约束每页 20 项、依赖最多 128 项、JSON 响应最多 8 MiB；成功快照缓存最多 64 项及 8 MiB，5 分钟过期，来源切换立即失效。输入 320 ms 去抖，网络/JSON/依赖解析和文件 I/O 不在 GUI 执行；文件复用原有受控并发和流式下载/摘要，成功清理本次暂存区，失败保留可重试文件。通用 Windows/macOS/Linux 架构基线不变，没有全局启用本机 AVX 指令。

query_cache_measurement 使用同一 Windows x64 Release 构建和同一内存 HTTP fixture，固定 15 ms 服务延时，连续七组“清缓存查询 → 同查询命中缓存”。每组两次查询只发一次 HTTP：14 次查询共 7 次 HTTP，命中请求从一次网络变为零次。最后一轮未命中中位 19.083 ms（18.552–20.784），命中中位 0.0212 ms（0.0196–0.0234），原始样本保存在实测 JSON。保留已有启动器及 IDE，没有隔离系统后台负载；完整回归期间也观察到更大计时波动。该对比衡量此查询缓存，包含固定模拟延时，不是启动器整体提速或真实公网倍率，也不代表 macOS/Linux 实测。
