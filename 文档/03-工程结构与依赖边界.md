# 工程结构与依赖边界

## 建议的单仓结构

    bugg/
      AGENTS.md                         # 开发约束
      .clang-format                     # 唯一 C++ 格式
      .editorconfig
      CMakeLists.txt                     # 后续原型阶段建立
      CMakePresets.json                 # Windows/macOS/Linux 各自可复现配置
      cmake/                             # 依赖锁定、打包规则、尺寸报告
      assets/                            # 精简图标、语言文本、无业务逻辑
      qml/
        Bugg/DesignSystem/               # 唯一 QML 组件库、令牌及 qmldir
        Bugg/Pages/                      # 首页/任务/下载/联机等布局
      src/
        app/                             # 进程入口与依赖组装；不写业务规则
        contracts/                       # 稳定 DTO、I*Port、错误码、任务事件
        platform/
          filesystem/                    # 原子写、锁、便携路径
          http/                          # 一处 HTTP/TLS/超时/取消
          archive/                       # ZIP 读取、路径保护与打包
          process/                       # Java、游戏、Bridge 子进程
          hashing/                       # SHA-1/SHA-256/SHA-512 流式校验
          logging/                       # 日志与脱敏
        modules/
          settings/ account/ java/ instances/ launch/
          catalog/ tasks/ download/ game_install/ modpack/
          multiplayer/ social/ room_sync/ update/ diagnostics/
          # 每个模块内部按 domain/ application/ infrastructure/ ui/ 分层
        shell/                            # QQmlApplicationEngine、导航、C++ 呈现模型
      tests/
        unit/ contract/ integration/ ui/
      tools/                             # 迁移检查、依赖图、体积报告
      文档/                              # 本规划及后续接口文档

目录图是目标所有权，不是现有代码快照。原生入口已接入真实微软认证、安装和游戏进程，当前所有者见本文末节及 [真实安装启动与生命周期流程](23-真实安装启动与生命周期流程.md)。已落地方法看 [已有方法与组件复用索引](18-已有方法与组件复用索引.md)。各模块应有自己的 CMake target；共享 platform 和 contracts 小而稳定，不设庞大 utilities.cpp。modules/*/ui 仅放 C++ 呈现模型，QML 页面统一放 qml/Bugg/Pages，避免两处 UI 文件来源。

## 依赖方向

    qml/Bugg/Pages + shell / modules/*/ui
           ↓
    modules/*/application  → contracts ← modules/*/domain
           ↓                         ↑
    modules/*/infrastructure → platform
           ↓
       Qt、原生 Bridge、文件系统、外部 API

应用层通过接口访问基础设施；实现由 app/ 依赖组装绑定。领域规则不引入 Qt Quick、HTTP 请求或磁盘路径。QML 只通过 C++ 呈现模型传命令、订阅不可变状态；不能直接触碰远程 API、Java 或目录删除。跨模块不能 include 另一个模块的 infrastructure/ 或 ui/，只能依赖 contracts/ 的显式服务接口。平台封装只提供机制，不藏业务规则。

## 唯一所有者

| 规则或资源 | 唯一所有者 | 对外契约；别处禁止做什么 |
| --- | --- | --- |
| 便携根目录、.minecraft 创建 | platform/filesystem/PortablePaths | 只通过路径对象取目录；别处不读环境变量推断缓存根 |
| 配置版本与保存 | modules/settings/SettingsRepository | 读写经 schema 与原子替换；页面不直接操作 JSON |
| 网络请求、超时、取消 | platform/http/HttpClient | 上层传 RequestContext；模块不再散写 QNetworkAccessManager |
| 来源顺序/能力补齐 | 当前 contracts/download_sources + modules/settings/ui/SourceSettings；后续文件策略扩展同一规则 | 适配器工厂消费统一计划；页面不拼 URL、不另存排序、不写重试循环 |
| 文件下载/哈希/断点 | modules/download/TransferService | 所有文件从此进入，写 .part 后原子落盘；别处不直接保存网络字节 |
| 任务状态/调度/持久化 | modules/tasks/TaskManager（应在结构中独立建模块） | 页面只持有 TaskId，不持有下载线程或“完成百分比”真相 |
| 实例路径/重名决策 | modules/instances/InstanceRepository | 导入、下载、房间同步复用同一命名/冲突策略 |
| Java 可执行文件选择 | modules/java/JavaSelectionService | 安装与启动均获取已验证 JavaExecutable，不传可能为空的路径 |
| 原生联机 RPC/协议版本 | modules/multiplayer/BridgeClient | 别的模块不读写 Bridge 标准流；协议变更只改适配器 |
| 节点选择/房间连接 | modules/multiplayer/NodeService、RoomService | 自动最低延迟可用节点，P2P→中转；页面不暴露连接策略开关 |
| 房间文件清单与授权 | modules/room_sync/RoomSyncService | 只传文件元信息，源站按策略决定重定向或请求实体 |
| 原生启动器更新（已落地） | modules/update/application/LauncherUpdateService | 唯一检查/暂存/安装状态；复用 HTTP、下载与安全文件机制，页面不替换文件，独立原生助手在退出后执行文件事务 |
| 视觉令牌/通用组件 | qml/Bugg/DesignSystem | 不在每页复制颜色、间距、弹窗与按钮实现；页面只 import 组件 |
| 窗口边缘吸附/折叠/展开避让 | qml/EdgeDock.qml；src/shell/DesktopEnvironment | 吸附、折叠状态和几何规则只在 EdgeDock；原生适配只读取屏幕工作区与鼠标状态，不在各工具片段复制拖动逻辑 |

对照现行项目：content_mirrors.py、content_routes.py、bugg_mirror.py 的策略进入下载模块；modpacks.py 的格式规则进入整合包模块；多处页面任务状态进入任务模块；hookup/native_* 的协议兼容收敛到 BridgeClient。映射细节见 [02-现状审计与功能清单](02-现状审计与功能清单.md)。

## 服务接口写法

每个公开服务只暴露用例层需要的最小能力，例如 TaskId DownloadService::enqueue(DownloadRequest)、void TaskManager::cancel(TaskId)、ConnectionResult RoomService::join(InviteCode)。契约需明确值对象、错误类型、是否异步、回调线程、可取消性、幂等性；具体命名以 [12-共享接口与能力目录](12-共享接口与能力目录.md) 为准。具体模块可有私有 helper，但不因两处“看着像”就造通用框架。

## 执行与线程

启动时序、账号/任务/页面寿命、折叠与关闭、异步取消和退出接线统一遵守 [启动器生命周期与资源管理](19-启动器生命周期与资源管理.md)。ApplicationLifecycle 已接入原生入口；新服务接同一协调器，不能各自持有退出等待循环。

Qt GUI 主线程只做事件分发、QML 绘制和短时状态更新。网络用 Qt 异步事件接口；哈希、解压、目录扫描与进程等待进有界工作池。线程的对象所有权由创建该对象的模块管理，不跨线程直接访问 QObject；结果用 queued signal 或可控任务回调回 GUI。取消优先标记并中止网络/进程工作，UI 立即解锁，后台负责安全清理 .part。参考 Qt 官方 [QNetworkAccessManager 线程说明](https://doc.qt.io/qt-6/qnetworkaccessmanager.html)。大列表暴露 QAbstractItemModel，页面不复制全量任务数组。

## 真实服务落地（2026-11-08）

实际文件在 src/app/application_lifecycle.*、modules/account/application/microsoft_account.*、modules/game_install/application/game_runtime.* 和 game_operations.*。当前实现使用这些明确所有者；上表尚未建立的 TransferService/TaskManager/JavaSelectionService 等为远期规划，禁止因规划名称另造同义服务。当前文件传输策略归 ResourceClient，传输机制归 HttpClient；任务/实例配置归 GameRuntime，Java 准备归 GameOperations；平台只负责检测、文件和进程机制。后续拆分必须迁移唯一实现及调用方，不允许并存两套流水线。流程/端口见第 23 份文档。
