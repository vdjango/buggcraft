# 联机与房间同步

## 一条用户路径

关联已开放世界：扫描完成后保留仍在候选列表中的手动选择；只有一个候选时默认选中，多个候选必须明确选择。扫描期间不可提交；扫描失败或候选消失时不得使用旧端口。失败保留建房草稿，重新查找清除旧错误。世界版本可含加载器展示前缀，但必须匹配完整游戏版本标记；房间元数据保留实例的规范游戏版本。发现与探测继续使用唯一异步 NativeBridge，不扫描或启动额外游戏进程。

进入大厅 → 后台挑可用低延迟节点 → 浏览器登录/恢复账号 → 选实例建房或输入邀请加入 → 比对客户端文件 → 缺什么补什么 → 进入世界。创建房间时若开启“文件共享加速”，必须在房主界面展示逐步进度和结果，不是静默后台上传。

## 模块责任

- **NodeService**：从可信目录获取节点及在线状态，启动和账号登录后在后台探测可用节点延迟，自动选择最低可用延迟；本次启动用户手动选择后保留。离线节点不出现在可选列表，网络变化时可重新评估。探测不在 GUI 线程，节点不可用给出回退状态。
- **IdentityService / SocialService**：身份授权、token 恢复与失效、好友、邀请、申请和聊天。切换账号先结束旧账号请求与订阅，再绑定新账号；旧账号好友/节点缓存不可直接呈现给新账号。授权成功自动回大厅。
- **BridgeClient**：唯一读写本地原生 Bridge 的 RPC 适配器，检查版本和方法清单、请求 ID、错误码、8,192 字节请求上限；流量、NAT 与中转由原生组件处理，UI 不暴露 transport 字段。
- **RoomService**：房间建立、加入、成员与游戏端口，状态为“未连接→准备→同步→就绪→游戏中→断开”。仅传 transport=auto；直连失败由 Bridge 切中转，显示实际路径；已有房间时禁止手动切节点。
- **RoomSyncService**：生成清单、按哈希差异形成缺失队列、请求 SourceResolver/DownloadService、处理房主文件兜底、报告同步进度。失败进入等待补齐，不能把“发了一份压缩包”当同步成功。

## 加入者文件顺序

本地已校验实体 → 用户排序的可用公网来源 → Buggcraft 源（如果不在前面的排序中）→ 经房主明确允许的房主文件/临时实体兜底。对每个候选校验房主清单哈希，任何来源字节不同都拒绝；成功文件绝不重复下载。这里的“源站实体”是服务端按清单要求单个上传后的临时缓存，不是整个客户端 ZIP。节点只做账号、房间、信令与 P2P/中继连接；源站负责普通资源重定向和必要时的文件缓存，两端通过授权和短期引用关联。

## 房主可见的加速流程

房间布局修订：聊天、成员、缓存（访客为游戏准备）共用 NavigationBar，小窗口分两行放导航与复制/邀请/主操作，常规窗口同排；安装准备与启动共用唯一主操作，按下文互斥状态切换。聊天输入为聊天视图最底部。房主开放世界指引替换页头的“等待世界开放”，连接后同位置绿色提示。Home 保留房间回启动页，右上返回图标离开当前房间回大厅，取消房间同步及缓存；不再在正文底部放关闭/启动或世界提示。

加入者先核对选中的本地配置，版本/加载器类型/模组内容不同则进入准备选择，沿用旧版“复用已有配置 / 全新安装”两条路径，均创建独立房间实例，不改原实例与存档。同类型加载器版本差异仅提示。成员可在房主未开放时准备和启动到主菜单；已开放时通过同一启动参数管线进入本机房间转发端口。同步完成只发布可启动状态，不自动启动。配置更新使旧校验/旧安装结果失效并取消所属任务；每次启动还在工作线程复核已绑定配置，不能只相信页面标签。具体类/方法契约在第 22 份文档维护。

1. 建房选择“加速缓存”，或在房间设置开启；本机权限在建房/configure 成功后保存到房间快照，节点 describe 省略该字段不能把开关重置。
2. 房主后台扫描白名单文件、计算哈希、取得节点签发的短期源站授权，UI 显示检查/连接状态；扫描与网络均在工作线程。
3. 源站依据策略决定公开源直下、等待或请求单个实体；客户端只上传 upload 清单明确请求的文件，不判断 512 KiB/s，不按速度切换来源。
4. 上传复用 HttpClient 的文件 PUT，显示当前文件、整批累计字节及进度；收到 SHA-256/大小匹配的缓存收据才增加已缓存数量，随后立即复查计划。关闭开关或离房取消同一任务并释放源站租约。
5. 房间复用 ProgressItem，完成后显示源站确认的缓存数量、公开源数量、待处理数量及已缓存的文件名；全走公开源、没有文件和服务不可用各有真实状态。源站未提供的持久保存时长、云端归档完成度不能伪造。加入者继续复用正常文件准备流程。

## 连接与失效

当前设备登录由 MultiplayerService 的 login → post/poll → approved → connect_profile 维护，页面只读 status。浏览器与启动器必须使用同一个 start 返回的请求 ID；只有 poll 返回 pending 才继续等待，approved 校验设备归属后立即切 connecting，再由 NativeBridge 的真实 node.add 结果进入 ready 或带错误的 signedOut。HTTP 200 内的 error、未知状态和无效配置都不能留在“等待浏览器授权”。轮询采用服务端 interval（1–30 秒边界），网络/协议失败、超时、取消及登出停止当前轮询，旧代次不能写回。

人工复现入口复用 runtime_test.live_node_authorization：BUGG_TEST_LIVE_NODE=1 与 BUGG_TEST_NODE_BROWSER_APPROVAL=1 才执行浏览器批准后的真实连接；BUGG_TEST_NODE_TRACE 可输出状态、授权链接及错误，不写节点配置、凭据和设备密钥。人工授权时设置 QTEST_FUNCTION_TIMEOUT=900000，避免 Qt Test 默认五分钟先于设备申请过期结束测试。自动协议联调可用 BUGG_TEST_NODE_ORIGIN 指向隔离测试节点、BUGG_TEST_NODE_CA 加入本进程的测试 CA；仍校验 HTTPS 证书，生产信任配置不变。常规无网络验收由同一 MultiplayerService、AuthHttp 和 BrowserProbe 覆盖 pending → approved → connecting、错误恢复及取消；不在 QML 或测试工具重写业务状态机。

原生运行依赖复用节点项目正式安装前缀 `../minecraft-tunnel-native/runtime`，由 BUGG_NATIVE_RUNTIME 指定；不默认使用历史 CI 解压目录。构建在引擎独立更新后也要刷新同一份 native/bin；CTest 的 native_bridge_runtime 必须实际执行随带引擎，防止只检查 exe 存在却遗漏 DLL 依赖。依赖闭包由原生项目安装规则维护，启动器不另写一套 DLL 推断规则。

不能选“强制中转”：统一自动 P2P→中转。5–10 人需测 NAT 组合与中继带宽；对称 NAT、UDP 不通时允许中转且说明路径；断线后会话重建，不能承诺已有 TCP 无损迁移。Bridge 掉线、节点身份过期、房主下线、网络改变要有明确可恢复状态。房间内未完成的必需模组禁止误启动；可选资源允许玩家确认跳过。真实联机、邀请、账号切换和同一模组跨两个房间的缓存引用是协议验收重点。

## 权限与安全

文件上传权限按节点身份和房间房主身份校验，源站返回单次短效上传授权；不把永久密钥放在 URL 或日志。文件清单只包含允许共享的相对路径，拒绝目录穿越、符号链接越界、无限制大文件。房主应看到是否可能分享私人文件；公开镜像的普通资源下载不强制用房主身份。设计与现有节点、源站 API 的差异必须先补协议兼容表再实现。

## 当前实现与界面边界（2026-11-09）

已落地：原生节点授权/恢复；真实目录房间、私密/公开准备房间、LAN 世界关联；短码/用户名查找及好友申请、邀请、加入申请；房间配置、成员移出/解除及管理权转让命令。统一由 MultiplayerService + NativeBridge 对接已有节点协议，页面只呈现/发意图。

本轮新增：原生房间聊天（发送确认、事件去重、离房清理）；加入者清单分页/摘要检查和白名单模组资源同步，复用 GameRuntime 队列与 GameOperations 安装、缓存、校验、原子发布；房主明确允许后才能 P2P 传文件。首页房间摘要、顶部世界信息和独立聊天/成员视图读取同一服务快照。

房间缓存已由 RoomContentCache 接入 room-content-cache-v1：授权、计划、按需上传、缓存/公开源解析、租约释放；成员准备进度复用真实安装/启动状态。线上样本已验证建房开启、源站请求上传、确认缓存、有效房间内下载及 SHA-256 一致，关闭/重开开关也通过。该结果不代表整套实例已缓存、云端长期归档或跨设备世界入场已完成；语音尚未实现。上文 RoomService/RoomSyncService 为职责规划，当前实现所有者是 MultiplayerService/GameRuntime/GameOperations/RoomContentCache，不增加同职责服务。具体证据和边界见第 25 份文档。

界面参考查阅 [Steam Matchmaking & Lobbies](https://partner.steamgames.com/doc/features/multiplayer/matchmaking) 与 [Epic Parties FAQ](https://www.epicgames.com/help/c-36624475/c-35761596/epic-parties-faq-a22007555)。资料支持成员、房主、邀请、加入条件和启动的职责划分；本项目当前采用顶部信息与操作、中部独立视图、聊天输入固定在最下方，并非文档规定的坐标。

另实际查看了 [Minecraft 官方多人游戏指南](https://www.minecraft.net/en-us/article/how-play-minecraft-server) 的 Bedrock 好友页及 Java 多人页截图：好友入口集中在列表上方，Java 操作固定在列表下方。参考截图保存在 build/ui-room-review/references；采用内容区与固定操作区的分离方式，未复制其像素风或按钮样式。


### 房间安装与启动互斥

参考旧版 `resources/qml/multiplayer/RoomHeader.qml` 的 room-quick-launch：同一主操作随配置变化，不并排提供“安装”和“启动”。未匹配为“同步安装”，只打开现有游戏准备视图；核对/准备期间显示过程状态，不能启动；当前配置匹配后才显示“启动游戏”，隐藏两种安装入口和已完成任务卡片。游戏视图保留当前实例与匹配结果；重新选择不匹配配置后恢复安装选项，原有实例不修改。失败在现有 TaskCard 重试，不再并排提供一组全新安装按钮。游戏运行和启动取消沿用 LaunchSession；不重写按钮校验。
